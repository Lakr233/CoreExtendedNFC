Singapore EZ-Link / CEPAS (experimental)

Traditional, non-SimplyGo CEPAS cards have an explicit read-only path for the purse and recent transaction log. iOS detection and physical-card reads are not yet verified. SimplyGo account-based history is not supported.

let manager = NFCSessionManager()
defer { manager.invalidate() }
let (_, transport) = try await manager.scan(for: [.iso14443])
guard let iso7816 = transport as? any ISO7816TagTransporting else {
    throw NFCError.tagNotSupported
}
let balance = try await CoreExtendedNFC.readSingaporeTransitBalance(transport: iso7816)

Use the dedicated API immediately after scanning; do not call refineCardInfo first, because its probes can change the selected application. The example app’s ISO 7816 AID list already contains A000000341000101 as an existing unverified candidate. No reliable CEPAS source has been established for this AID, and its declaration does not prove that Core NFC can discover a CEPAS card.

The reader uses the standard five-byte GET PURSE encoding accepted by Core NFC. Older cards may reject it with 6700; the historical six-byte variant is rejected by NFCISO7816APDU(data:) in the iOS Simulator. See the protocol findings.

First physical-card test

  1. Use one traditional EZ-Link card that has not been upgraded to SimplyGo. Photograph or record its ticket-machine balance and two known recent journeys, including their dates, times, amounts, and stations or bus routes.
  2. Run the example app on an NFC-capable iPhone. Turn off Wi-Fi and cellular data, then open Tools → Transit Balance → Test Singapore EZ-Link / CEPAS. Keep only that card near the phone.
  3. Compare the displayed balance and recent records with the reference. Singapore transaction times are shown in Singapore time. Signed balance changes are displayed in SGD cents; a missing post-transaction balance is omitted because CEPAS logs do not provide it.
  4. Open Logs and export the existing text/JSON log bundle. It includes session outcome, initial AID when detected, and APDU traffic. Record the iPhone model, iOS version, card type, and reference journeys with the test result.
  5. Record detection failures, protocol errors, and mismatches as failures. Only mark a card as verified after an offline read matches its balance and both known journeys; simulator and mock tests cannot establish physical-card support.
